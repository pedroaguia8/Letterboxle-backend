# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Go backend for Letterboxle, a daily Wordle-style movie-guessing game. Serves a JSON API consumed by a separate React frontend, backed by PostgreSQL. Live at letterboxle.pedroaguia8.dev.

## Commands

```bash
# Run
go build -o app && ./app                        # requires .env (see below) or env vars set
docker compose -f docker-compose.dev.yml up -d  # start local dev Postgres (app itself still runs natively, not in Docker)

# Test (needs the dev Postgres running and TEST_DB_URL in .env)
go test ./... -cover              # full suite
go test ./internal/handlers/...   # single package
go test ./internal/handlers/... -run TestDbMovieOfTheDayToMovie   # single test

# Quality (all run in CI)
go fmt ./...
staticcheck ./...
gosec ./...

# Database
go build -o app && ./app migrate               # apply migrations (embedded in the binary; no goose CLI needed)
sqlc generate                                    # regenerate internal/database from sql/schema + sql/queries after editing either
```

Required env vars (`.env` in dev — copy `.env.example`, injected as secrets in CD): `DB_URL`, `TMDB_API_READ_ACCESS_TOKEN`, `PLATFORM`, `PORT`, `FIREBASE_PROJECT_ID`, `FIREBASE_SERVICE_ACCOUNT` (the Firebase Admin SDK service account key JSON, base64-encoded to fit on one line; unused until Firebase Auth wiring lands).

Tests use their own variable, `TEST_DB_URL` (in `.env` locally, set by `ci.yml` in CI): a Postgres server, reached through its default `postgres` database, where tests create and drop their own throwaway databases. It's never the app's `DB_URL`. Tests fail (not skip) if it's missing or unreachable. CI runs a disposable Postgres service container for it.

`docker-compose.yml` is prod-shaped (builds the app image, joins the external `npm` network) and is only ever run by `cd.yml` on the prod host — never run it locally, it'll fail (no `npm` network exists locally). `docker-compose.dev.yml` is unrelated to it (not an override/layer) and only provides a disposable local Postgres for development.

## Architecture

- **main.go** wires everything: loads env, opens the DB, embeds `sql/schema/*.sql` (`//go:embed`), handles the `migrate` subcommand (`./app migrate` applies pending migrations via `internal/migrations` and exits), refuses to start if the DB has pending migrations, starts the catalog syncer and selection background workers, registers HTTP routes on `http.ServeMux`, and handles graceful shutdown on SIGINT/SIGTERM.
- **internal/database** is entirely generated by `sqlc` from `sql/schema/*.sql` (goose migrations) and `sql/queries/*.sql`. Never hand-edit files here — change the `.sql` sources and rerun `sqlc generate`.
- **internal/handlers** holds the HTTP layer (`ApiConfig` methods bound as handlers) and DTO mapping between generated DB row structs and the API's `Movie`/`movieDto` JSON shapes. `utils.go` has the shared `RespondWithJSON`/`RespondWithError` helpers all handlers funnel through, plus `posterURL` (builds the full TMDB image URL from a stored `poster_path`) and `genreNames` (unpacks the `genres` JSONB column into `[]string`).
- **internal/tmdb** is the TMDB API client, with two endpoints: `DiscoverMovies` (paginated `/discover/movie`, used to walk the catalog by `vote_count.gte`) and `GetMovieDetails` (`/movie/{id}?append_to_response=credits`, pulls director + top-2-billed cast out of `credits` and keeps every other nested TMDB object — genres, production companies, etc. — as raw JSON for the matching JSONB columns). All requests share one `do`/`doGet` path that throttles to 30 req/s and retries on 429 honouring `Retry-After`. `baseURL` is overridable via `SetBaseURL` for testing against a mock server. `ImageBaseURL` is the constant handlers prepend to a stored `poster_path` to build a poster URL.
- **internal/workers** has two workers, both started from `main.go`: `CatalogSyncer`, whose `Sync` walks the full TMDB discover list (`vote_count.gte=5000`, sorted by `vote_count.desc`), diffs returned ids against `movies` (`GetAllMovieIDs`), and fetches+inserts anything new — runs once at startup (seeding an empty catalog) then weekly (keeping it current, since re-walking the full list is cheap, ~50 calls), retrying after 5 min on failure; and `Selector`, whose `Fill` keeps `movie_of_the_day` populated 7 days out (`SelectionWindowDays`) by picking a random unused, eligible movie (`PickRandomUnusedMovie`) for any missing date — runs at startup then every 4 hours, retrying after 1 min if it fails or if the window isn't fully filled (e.g. the catalog sync hasn't caught up yet) since `Fill` is cheap and idempotent, and logs a warning when the eligible-unused count drops below 30.
- "Eligible" means every hint column (`tagline`, `genres`, `director`, `actor1`, `actor2`, `year`, `poster_path`) is non-null **and** `adult`/`video` are not true. That filter is duplicated by hand in `PickRandomUnusedMovie` and `CountEligibleUnusedMovies` (and the adult/video part in `ListAllMovies`) in `sql/queries/movies.sql`, so change all of them together.
- The `movie_of_the_day` table maps a date to a `movies.id` (unique, so a movie is never reused); there's currently no support for playing past days (`GetMovieOfTheDay` rejects any date param other than `"today"`). "Today" is the UTC date.
- `movies.genres` and the other nested TMDB fields (`credits_cast`, `credits_crew`, `production_companies`, `belongs_to_collection`, etc.) are JSONB columns holding TMDB's raw objects verbatim. `handlers.genreNames` unpacks `genres` into a `[]string` of names for the API DTO; ids stay in the DB unused for now, kept for future filtering.
- `GET /api/movies` (`ListMovies`) returns the full lightweight movie list (id, title, year) with a `Cache-Control` header, for the frontend to fetch once and filter client-side; there's no server-side search endpoint anymore.

## Migrations

- **Every migration must be backward-compatible with the code already deployed (expand/contract).** During a deploy, old code and the new schema briefly run together, and rolling back to a previous image rolls back the code but not the schema. So a breaking change is split across deploys: first add the new thing (nullable column, new table) and ship code that stops depending on the old thing; only in a later deploy drop or rename the old column or tighten the constraint. Never drop or rename something the currently deployed code still reads or writes.
- Prod is forward-only: never edit a migration that has already run in prod, and fix mistakes with a new migration. Down blocks are for local dev only.

## CI/CD

- `ci.yml`: on PR/push to `main`, runs tests+gosec and separately fmt+staticcheck.
- `cd.yml`: triggers on the `ci` workflow completing successfully on `main` (not directly on push), then SSHes (via cloudflared tunnel) into the prod host, pulls, rewrites `.env` from secrets, builds the image, runs `app migrate` in a throwaway container (`docker compose run --rm`) while the old app keeps serving, and only then switches over with `docker compose up -d`. If migrations fail the deploy stops there.
- The frontend repo (`../Letterboxle-frontend`) has its own `ci.yml`/`cd.yml` built the same way. They deploy to `~/Letterboxle-frontend` on the same host and use the same four `SSH_*` secrets, which are set separately in each repo. The only key in the host's `authorized_keys` is the personal `id_ed25519`, so both repos' `SSH_PRIVATE_KEY` hold that key.

## Git workflow

- `main` is the only long-lived branch. Every change goes on a short-lived branch and into `main` through a PR, never as a direct push. Merging to `main` deploys to prod.
- Merge PRs with a rebase merge (linear history, no merge commits), and delete the branch once it's merged.
- Don't leave branches lying around. If one exists, check whether it's already in `main` (`git log main..<branch>`) and either open a PR for it or delete it.
- The same rules apply to the frontend repo (`../Letterboxle-frontend`).
