## Project overview

Go backend for Letterboxle, a daily Wordle-style movie-guessing game. Serves a JSON API consumed by a separate React frontend, backed by PostgreSQL. Live at letterboxle.pedroaguia8.dev.

## Commands

```bash
# Run
go build -o app && ./app                        # requires .env (see below) or env vars set
docker compose -f docker-compose.dev.yml up -d  # start local dev Postgres (app itself still runs natively, not in Docker)

# Test
go test ./... -cover              # full suite
go test ./internal/handlers/...   # single package
go test ./internal/handlers/... -run TestDbMovieOfTheDayToMovie   # single test

# Quality (all run in CI)
go fmt ./...
staticcheck ./...
gosec ./...

# Database
goose -dir sql/schema postgres "$DB_URL" up     # apply migrations
sqlc generate                                    # regenerate internal/database from sql/schema + sql/queries after editing either
```

Required env vars (`.env` in dev — copy `.env.example`, injected as secrets in CD): `DB_URL`, `TMDB_API_READ_ACCESS_TOKEN`, `PLATFORM`, `PORT`.

`docker-compose.yml` is prod-shaped (builds the app image, joins the external `npm` network) and is only ever run by `cd.yml` on the prod host — never run it locally, it'll fail (no `npm` network exists locally). `docker-compose.dev.yml` is unrelated to it (not an override/layer) and only provides a disposable local Postgres for development.

## Architecture

- **main.go** wires everything: loads env, opens the DB, starts the catalog syncer and selection background workers, registers HTTP routes on `http.ServeMux`, and handles graceful shutdown on SIGINT/SIGTERM.
- **internal/database** is entirely generated by `sqlc` from `sql/schema/*.sql` (goose migrations) and `sql/queries/*.sql`. Never hand-edit files here — change the `.sql` sources and rerun `sqlc generate`.
- **internal/handlers** holds the HTTP layer (`ApiConfig` methods bound as handlers) and DTO mapping between generated DB row structs and the API's `Movie`/`movieDto` JSON shapes. `utils.go` has the shared `RespondWithJSON`/`RespondWithError` helpers all handlers funnel through, plus `posterURL` (builds the full TMDB image URL from a stored `poster_path`) and `genreNames` (unpacks the `genres` JSONB column into `[]string`).
- **internal/tmdb** is the TMDB API client, with two endpoints: `DiscoverMovies` (paginated `/discover/movie`, used to walk the catalog by `vote_count.gte`) and `GetMovieDetails` (`/movie/{id}?append_to_response=credits`, pulls director + top-2-billed cast out of `credits` and keeps every other nested TMDB object — genres, production companies, etc. — as raw JSON for the matching JSONB columns). All requests share one `do`/`doGet` path that throttles to 30 req/s and retries on 429 honouring `Retry-After`. `baseURL` is overridable via `SetBaseURL` for testing against a mock server. `ImageBaseURL` is the constant handlers prepend to a stored `poster_path` to build a poster URL.
- **internal/workers** has two workers, both started from `main.go`: `CatalogSyncer`, whose `Sync` walks the full TMDB discover list (`vote_count.gte=5000`, sorted by `vote_count.desc`), diffs returned ids against `movies` (`GetAllMovieIDs`), and fetches+inserts anything new — runs once at startup (seeding an empty catalog) then weekly (keeping it current, since re-walking the full list is cheap, ~50 calls), retrying after 15 min on failure; and `Selector`, whose `Fill` keeps `movie_of_the_day` populated 7 days out (`SelectionWindowDays`) by picking a random unused, eligible movie (`PickRandomUnusedMovie`) for any missing date — runs at startup then every 4 hours, also retrying after 15 min on failure, and logs a warning when the eligible-unused count drops below 30.
- The `movie_of_the_day` table maps a date to a `movies.id`; there's currently no support for playing past days (`GetMovieOfTheDay` rejects any date param other than `"today"`).
- `movies.genres` and the other nested TMDB fields (`credits_cast`, `credits_crew`, `production_companies`, `belongs_to_collection`, etc.) are JSONB columns holding TMDB's raw objects verbatim. `handlers.genreNames` unpacks `genres` into a `[]string` of names for the API DTO; ids stay in the DB unused for now, kept for future filtering.
- `GET /api/movies` (`ListMovies`) returns the full lightweight movie list (id, title, year) with a `Cache-Control` header, for the frontend to fetch once and filter client-side; there's no server-side search endpoint anymore.

## CI/CD

- `ci.yml`: on PR/push to `main`, runs tests+gosec and separately fmt+staticcheck.
- `cd.yml`: on push to `main`, SSHes (via cloudflared tunnel) into the prod host, pulls, rewrites `.env` from secrets, rebuilds via `docker compose up -d --build`, then runs goose migrations inside the container.
